# Zabbix: мониторинг инфраструктуры и SMART-дисков по 18 подсетям

Централизованный мониторинг Windows-рабочих станций на 18 удалённых площадках (каждая в своей подсети) с упором на раннее обнаружение проблем с дисками: чтобы отказ железа замечался до потери данных и простоя.

## Задача

- Развернуть агенты на всех рабочих станциях без ручной установки.
- Автоматически находить и заводить хосты по всем подсетям.
- Следить за состоянием дисков (SSD, NVMe, HDD) через SMART.
- Не засорять мониторинг лишними метриками.

## Стек

- Zabbix Server, Zabbix Agent 2
- smartmontools (SMART-данные на Windows)
- GPO (массовое развёртывание агентов)
- Python 3 + `requests` (автоматизация через Zabbix API)
- cron + logrotate (плановый запуск скриптов на сервере)
- JavaScript preprocessing и LLD в Zabbix

## Структура репозитория

```
zabbix-monitoring/
├── README.md
├── templates/
│   ├── smart-by-zabbix-agent-2-custom.yaml     # клон SMART-шаблона с фиксом disk_type и порогов по типу диска
│   └── windows-by-zabbix-agent-2-custom.yaml   # урезанный Windows-шаблон (см. п. 2)
└── scripts/
    ├── fix_interface_ip.py   # дозаполняет IP в Agent-интерфейсе по system.hostname
    ├── rename_ip_hosts.py    # переименовывает хосты вида "10.x.x.x" в реальное имя, дубли удаляет
    └── run_all.sh            # запускает оба скрипта по расписанию и пишет лог
```

## Что сделано

### 1. Развёртывание агентов через GPO
Тихая установка Zabbix Agent 2 и smartmontools на Windows-станции групповой политикой. Отдельно решена проблема повторной установки: остаточный ключ реестра `SYSTEM\CurrentControlSet\Services\EventLog\Application\Zabbix Agent 2` блокирует переустановку, поэтому он чистится перед установкой.

### 2. Оптимизация шаблона
Склонирован и урезан шаблон «Windows by Zabbix agent», файл [`templates/windows-by-zabbix-agent-2-custom.yaml`](templates/windows-by-zabbix-agent-2-custom.yaml):
- отключено обнаружение физических дисков стандартным способом (вместо него своя SMART-логика);
- сокращены счётчики сетевых интерфейсов;
- обнаружение служб Windows сужено до белого списка через макрос `{$SERVICE.NAME.MATCHES}`.

### 3. Автообнаружение (Discovery)
Правила и действия (Actions) настроены для всех 18 подсетей. Действия создавались массово Python-скриптом через API: структура клонируется с эталонного действия, а не собирается вручную из числовых констант.

### 4. Наведение порядка в хостах
- Хостам, добавленным вручную ранее, пакетно добавлены интерфейсы Agent и шаблоны через `host.massadd`.
- Дубликаты, которые Discovery создал с именем в виде IP, разбираются скриптами [`scripts/fix_interface_ip.py`](scripts/fix_interface_ip.py) и [`scripts/rename_ip_hosts.py`](scripts/rename_ip_hosts.py):
  - `fix_interface_ip.py` дозаполняет пустой IP в Agent-интерфейсе хоста. Сначала сверяет DNS-имя интерфейса с последним значением элемента данных `system.hostname` (реальное имя компьютера по мнению Windows), и если они расходятся, помечает хост на ручную проверку вместо автоматической правки. Резолвит DNS-имя через `socket.gethostbyname` и пишет результат в интерфейс.
  - `rename_ip_hosts.py` находит хосты, у которых «Имя узла сети» это голый IP (Discovery создаёт такие, если резолвинг DNS ещё не произошёл), и переименовывает их в `system.hostname`. Если хост с этим именем уже существует, дубликат с именем-IP удаляется.
  - `run_all.sh` запускает оба скрипта по очереди и пишет лог; используется как задача cron (см. п. 6).

### 5. SMART-мониторинг без скриптов на хостах
Реализован полностью средствами Zabbix, шаблон [`templates/smart-by-zabbix-agent-2-custom.yaml`](templates/smart-by-zabbix-agent-2-custom.yaml): клон официального `SMART by Zabbix agent 2` с доработками под этот проект — зависимые элементы данных (Dependent items) и JavaScript-предобработка поверх стандартного мастер-элемента `SMART [{#NAME}]: Get disk attributes`.

| Тип диска | Что отслеживается |
|---|---|
| SATA SSD | остаток ресурса (SSD life left) |
| NVMe | остаток ресурса (100 − percentage_used) |
| HDD | переназначенные секторы, ожидающие секторы, неисправимые ошибки |

Пороги температуры задаются через контекст LLD-макросов по типу диска.

### 6. Серверные скрипты по расписанию
Скрипты лежат в `/root/zabbix-scripts/`, запускаются по cron (`0 18 * * 2,5`, вторник и пятница), логи ротируются через logrotate (`weekly`, `rotate 2`).

## Грабли и решения

- **`host.get`**: группы хоста возвращаются в поле `hostgroups` (всё строчными), а не `hostGroups`.
- **Discovery Action через API**: `conditions` и `evaltype` нужно вкладывать внутрь объекта `filter`, а не на верхний уровень.
- **Макрос обнаружения служб**: значение `NOT_MATCHES = ^.*$` молча блокирует всё, включая белый список. Нейтральное значение: `^$`.
- **SMART, JS-предобработка**: перед чтением `percentage_used` обязательно проверять `data.disk_type`. Поле есть в JSON любого диска, и без проверки HDD ложно показывали «SSD Life Left = 100».
- **Контекст LLD-макроса**: кавычки вокруг макроса обязательны: `{$SMART.TEMPERATURE.MAX.WARN:"{#DISKTYPE}"}`. Без них Zabbix выдаёт ошибку разбора.
- **`host.massadd` вместо `host.update`**: `update` заменяет существующие шаблоны и интерфейсы, `massadd` только добавляет.
- **Кэш сервера**: массовые операции переполняли кэш, помогло `CacheSize=256M` в `zabbix_server.conf`.
- **Служба Zabbix вечно в состоянии «activating»**: причиной был разный путь `PIDFile` в `override.conf` и в `zabbix_server.conf`. Пути выровнены.
- **Подход к API-скриптам**: брать эталонный рабочий объект и клонировать его структуру, а не угадывать числовые константы типов.
